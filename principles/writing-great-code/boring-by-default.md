# boring-by-default

A team gets about three innovation tokens; everything else should be proven
technology.

Use when a plan or change introduces new infrastructure, a new framework, a
novel architecture pattern, or a custom build of something that exists.

## Actions

1. Count what novel technology the plan already carries before adding more.
2. Treat each novel component as spending a token — name what the spend buys.
3. Prefer the boring, proven option when the novel one buys no bounded,
   articulable advantage.
4. A custom solution where a built-in or battle-tested tool exists is a
   scope-reduction finding, not a preference.

## Evidence

Name the innovation spends in the plan/review and the justification recorded
for each.

## Failure Smells

- New datastore, queue, or framework for a problem the current stack handles.
- "We might need the flexibility" with no second concrete use.
- Novelty stacked on novelty — an unproven tool operated by an unproven
  pattern.
